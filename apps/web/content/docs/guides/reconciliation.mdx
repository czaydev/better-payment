---
title: Reconciliation
description: List a provider's daily transactions, normalize them and match them against your own orders, without changing any payment.
---

The reconciliation API answers one question for a day: **what did the provider actually settle?** It catches payments that succeeded while the callback was lost, refunds made from the provider panel, fees, and orders the provider never charged. It is read-only: it never creates, refunds, cancels or re-executes a payment, and it never changes an order's status.

## Quick start

Add a source for every provider you want to report on and register the plugin. The provider id and the source id must match.

```typescript
import { betterPayment, paytr } from 'better-payment';
import { paytrReconciliation, reconciliationPlugin } from 'better-payment/reconciliation';

const paytrConfig = {
  merchantId: process.env.PAYTR_MERCHANT_ID!,
  merchantKey: process.env.PAYTR_MERCHANT_KEY!,
  merchantSalt: process.env.PAYTR_MERCHANT_SALT!,
};

const payment = betterPayment({
  providers: { paytr: paytr(paytrConfig) },
  plugins: [reconciliationPlugin({ sources: [paytrReconciliation(paytrConfig)] })],
});

const day = '2026-10-19';
const transactions = await payment.listTransactions({ from: day, to: day });

const report = await payment.reconcile({
  from: day,
  to: day,
  orders: [{ orderId: 'ORD-1', amount: '149.90', currency: 'TRY', status: 'success' }],
});

console.log(report.matched, report.mismatched, report.missingInProvider);
```

`listTransactions()` returns provider rows with `provider`, `transactionId`, `orderId`, `type` (`sale`, `refund`, `void`, `settlement`, `other`), `amount`, `fee`, `currency`, `status` and `date`. Amounts are decimal strings in the currency's minor units (`"149.90"` for TRY, `"1500"` for JPY), never floats. Rows carry no card number or customer data.

Calling `payment.listTransactions()` asks every configured source. Pass `provider` to ask one, or call the operation on a provider (`payment.paytr.listTransactions()`) to use that provider's source only.

Without the plugin, use the standalone facade:

```typescript
import { createReconciliation, iyzicoReconciliation } from 'better-payment/reconciliation';

const reconciliation = createReconciliation({
  sources: [
    iyzicoReconciliation({
      apiKey: process.env.IYZICO_API_KEY!,
      secretKey: process.env.IYZICO_SECRET_KEY!,
      // iyzico's public docs do not enumerate the report's status codes. Map the
      // successful code of your account, or every row stays `unknown`.
      statusMap: { '2': 'success' },
    }),
  ],
});

const orders = await loadOrders('2026-10-19'); // your own order store
const report = await reconciliation.reconcile(orders, { from: '2026-10-19', to: '2026-10-19' });
```

## How matching works

Orders are matched to provider rows by `orderId`. The report classifies every order and every transaction, and never resolves an uncertain case:

| Report field | Meaning |
| --- | --- |
| `matched` | The order and a provider sale agree on id, amount and currency. `providerStatus` is `confirmed` only when the provider's row is successful; `unknown` means the report did not state a status, so treat the money as unverified. |
| `mismatched` | The order exists at both sides but disagrees: `amount`, `currency`, `status`, `refund` (the refunds do not cover a refunded order) or `order-not-marked-success` (the provider settled a payment your order still marks pending or failed). |
| `missingInProvider` | An order you mark paid or refunded with no provider transaction at all. |
| `unknownInMerchant` | A sale, refund or void with no local order: a panel refund, a lost callback, or a transaction for another system. |
| `ambiguous` | Several successful sales share one order id, which may be a double charge. Both are listed; none is picked. |
| `duplicateTransactionIds` | Rows delivered twice by page or window overlap. Each is counted once in the report and in the totals. |
| `totals` | Sales, refunds, fees and transaction count per currency, as exact decimal strings. |

An order marked `failed` with no charge, or `cancelled` with no charge, is consistent and appears in `matched`. A cancelled order that was charged shows up as `mismatched` unless a void or refund covers it. Reconcile never changes either side; review the report and fix your records yourself.

## Provider support

A provider is supported only when its own public documentation describes a date-range transaction report. The normalized source is in `better-payment/reconciliation`.

| Provider | Source | Notes |
| --- | --- | --- |
| PayTR | `paytrReconciliation()` | `/rapor/islem-dokumu`; windows of at most 3 days. The report has no unique row id, so the id is a deterministic composite of order, date, type and amount. |
| iyzico | `iyzicoReconciliation()` | Reporting API, one day per request. Basket-item rows are summed per payment id and type by default; set `aggregateByPayment: false` to keep raw rows. Status codes need `statusMap`, otherwise rows are `unknown`. |
| Akbank | `akbankReconciliation()` | txnCode 1009, one day per request. A day with more than 9999 rows answers `VPS-2235`; set `batchStep` to page through it, or the call fails instead of returning a truncated day. |
| Parampos | `paramposReconciliation()` | `TP_Islem_Izleme`, whole window in one response. Amounts and dates use Param's comma and `dd.MM.yyyy HH:mm:ss` formats. |

All other providers (`sipay`, `qnbpay`, `est`, `isbank`, `ziraat`, `halkbank`, `teb`, `sekerbank`, `akbankest`, `halkbankmkd`, `denizbank`, `vakifbank`, `yapikredi`, `qnb`, `kuveytturk`, `albaraka`, `mock`) answer `NOT_SUPPORTED`. Their public documentation, checked in October 2026, does not describe a date-range transaction report. If your account exposes one, write a custom `ReconciliationSource`; the plugin accepts any source id.

None of the four documented reports returns a settlement or payout date, so the normalized row has none. Dates are the provider's local transaction time, normalized to `YYYY-MM-DDTHH:mm:ss` (or `YYYY-MM-DD` when the report has no time). A query may cover at most 92 days; each source splits it into the windows its provider accepts.

## Scheduled daily job

Reconciliation is safe to rerun: it only reads. Trigger it once a day after the provider has closed the previous day, pass your orders from the database, and store the report for review. The payment-records API (#116) is not part of this release; until it lands, supply the merchant side from your own order store.

```typescript
// app/api/reconcile/route.ts
import { NextResponse } from 'next/server';
import { createReconciliation, paytrReconciliation } from 'better-payment/reconciliation';

const reconciliation = createReconciliation({
  sources: [
    paytrReconciliation({
      merchantId: process.env.PAYTR_MERCHANT_ID!,
      merchantKey: process.env.PAYTR_MERCHANT_KEY!,
      merchantSalt: process.env.PAYTR_MERCHANT_SALT!,
    }),
  ],
});

export async function GET(request: Request) {
  if (request.headers.get('authorization') !== `Bearer ${process.env.CRON_SECRET}`) {
    return new NextResponse('Unauthorized', { status: 401 });
  }

  // Yesterday in UTC; adjust if your provider closes the day in local time.
  const day = new Date(Date.now() - 86_400_000).toISOString().slice(0, 10);
  const orders = await loadOrders(day);
  const report = await reconciliation.reconcile(orders, { from: day, to: day });

  await saveReport(day, report);
  return NextResponse.json({
    matched: report.matched.length,
    mismatched: report.mismatched.length,
    missingInProvider: report.missingInProvider.length,
    unknownInMerchant: report.unknownInMerchant.length,
  });
}
```

On Vercel, schedule the route with a cron entry:

```json
{
  "crons": [{ "path": "/api/reconcile", "schedule": "15 3 * * *" }]
}
```

Alert on `mismatched`, `missingInProvider` and `unknownInMerchant`; those are the cases that need a human. Do not mark an order paid from a report — compare it with what the provider confirms and with your own records.

## Safety rules

- `reconcile()` is pure and read-only; it returns a report and changes nothing. It is not a payment or refund operation.
- A provider row is `success` only when the provider says so. iyzico rows without a mapped status stay `unknown` and produce `providerStatus: 'unknown'`, not a confirmation.
- Amounts are compared in integer minor units, so 0-decimal currencies such as JPY and 3-decimal overrides are exact.
- Duplicate rows are removed by `provider` + `transactionId`; rerunning a day, or two overlapping windows, cannot double-count.
- When two successful sales share an order id, the order is `ambiguous`; the library does not decide which charge is real.
- Sources throw `ReconciliationError` with code `RECONCILIATION_ERROR`. Messages carry the provider's error code only, never the response body, which contains order data and PII.
- A provider without a configured source throws `NOT_SUPPORTED` before any request is made.
