better-payment is a payment orchestration library that runs inside your application. It gives one API to many Turkish providers, verifies their callbacks and lets plugins add routing, failover and automation. It is not a payment institution and it does not move money itself.

This page answers the questions people ask when they compare it with a commercial orchestration platform: which features exist today, which are in review or planned, and what is out of scope on purpose.

Statuses below are for the `beta` branch. The linked issue or pull request is the source of truth; when one ships, its row changes.

## What better-payment will not do [#what-better-payment-will-not-do]

These limits come from what the library is: code that runs in your process, under your PCI DSS scope, with your provider contracts.

### A shared card vault across providers [#a-shared-card-vault]

Storing raw card numbers so any provider can charge them later would put your own servers in full PCI DSS scope and make the library a card-data processor. That is a business most merchants should not enter. Stored cards are provider tokens: the provider holds the card, returns a token, and you charge that token through the stored-card API ([#27](https://github.com/czaydev/better-payment/issues/27)). See also [#151](https://github.com/czaydev/better-payment/issues/151) and [#65](https://github.com/czaydev/better-payment/issues/65).

### Moving money between parties [#moving-money-between-parties]

Paying sub-merchants, holding wallet balances and making payouts require a payment or e-money institution licence (Law No. 6493 in Turkey). The library can calculate and record each party's share for a marketplace payment ([#88](https://github.com/czaydev/better-payment/issues/88), [#116](https://github.com/czaydev/better-payment/issues/116)), but the transfer itself is executed by a licensed provider.

### Fraud scoring as a service [#fraud-scoring-as-a-service]

better-payment ships rules you write and control ([#105](https://github.com/czaydev/better-payment/issues/105)), not a risk model trained on other merchants' traffic. A scoring service needs a data platform, a model and a team to run it; a library that silently made risk decisions would be harder to audit, not easier.

## PCI DSS: which models keep card data off your server [#pci-dss-which-models-keep-card-data-off-your-server]

The integration model decides how much of PCI DSS applies to you:

- **Card data never touches your server:** iyzico's hosted payment form, PayTR's iframe 3D Secure mode, and bank 3D Secure models where the shopper enters the card on the bank's page (for example Akbank 3D_PAY). Your server only sees the callback, verifies it and reads the result.
- **Card data touches your server:** a direct API integration with your own card form, like the example shop in this repository. The card is posted to your handler and forwarded to the provider. This is the shortest integration to build and the heaviest in compliance terms: it brings your server into PCI DSS scope (SAQ D), and you must never log or store the card.
- **Tokens instead of cards:** after a successful payment the provider can return a token. Stored cards are tokens; the card number never comes back to you.

For production, prefer a hosted or iframe model unless you have a reason to handle card data yourself. The [test cards](/docs/guides/test-cards) page lists the sandbox values that work in either model.
